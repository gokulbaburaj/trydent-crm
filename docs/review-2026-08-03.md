zero `TODO`s, zero `console.log`, two `as any` in 47,000 lines, real admin

## Cancel

### 1. `src/components/charts/` — the single biggest call on this list

16,882 lines across ~85 files. Roughly 36% of everything you have written.

What it is actually used for: **twelve** entry points, imported by three pages
(`organization`, `pipeline`, `dashboard`) — `pie-chart`, `pie-slice`,
`pie-center`, `bar-chart`, `bar`, `bar-x-axis`, `grid`, `line-chart`,
`area-chart`, `x-axis`, `chart-loading-label`, `tooltip`.

So you are carrying a full bespoke charting framework — projection lines,
reveal clips, phase orchestrators, shimmer hooks, decimation, ring charts,
funnel charts, dash-tail overlays — to draw some pie charts and bar charts. The
funnel chart alone is 1,041 lines and I can't find a page importing it.

This is the most expensive thing in the repo and it earns the least. Every one
of those files is code you own, debug, and typecheck forever.

**Do this:** keep the twelve components that are used, delete the rest, and let
the survivors sit directly on `@visx` (already a dependency). If that's more
surgery than you want, the alternative is to replace all twelve with Recharts
and delete the directory outright. Either way this should be a scheduled piece
of work, not something done opportunistically — it's the highest-leverage
cleanup available and it will feel enormous in the diff.

I would not attempt this without first putting the three consuming pages in
front of you side by side, before and after.

### 2. Dead and duplicate dependencies

Verified by grepping `src/` **and** `globals.css` (per the standing rule):

- **`lodash`** — zero imports anywhere. Dead. Remove.
- **`@radix-ui/react-popover`** — zero imports. `shadcn/popover.tsx` uses the
  `radix-ui` umbrella package instead. Remove.
- **`@radix-ui/react-toolbar`** — *keep*. `shadcn/toolbar.tsx` imports it
  directly. This is exactly the case the standing rule exists for.
- **`tw-animate-css`** — *keep*. Zero imports in `src/`, but it's in
  `globals.css`. Second time that check has earned its place.

**Two animation libraries.** `motion` has 44 import sites. `animejs` has
exactly one, in `lib/motion.ts`. Pick one — `motion` on volume — and port that
single call site.

**`next-themes`** — one import, in `shadcn/sonner.tsx`, on an app that is
dark-only. `globals.css` has a comment that depends on its behaviour, so verify
before touching. Low value either way; listed for completeness.

### 3. Three handoff documents

`AUDIT.md` (303 lines, historical, explicitly not to be updated), `HANDOFF.md`

Collapse the three handoff docs into one. Move `AUDIT.md` to `docs/archive/`
so its status is obvious from its path rather than from a line inside it.

## Improve

### 1. Tests — the real gap

Zero tests across 47,000 lines. I am not going to recommend chasing coverage;
on a product at this stage that's the wrong trade. But **pure logic must be
tested**, and the last two days make the case better than I can.

Yesterday's punchlist said the Schedule week grid had no collision clustering.
It does — `layoutDay` implements the standard algorithm correctly. I only found
that out by porting the function into a throwaway node script and running five
cases through it. That script should not have been throwaway.

The functions that deserve tests, today: `layoutDay` (schedule), the date maths
in `lib/taskTime.ts`, `lib/permissions.ts` (`isPortalOnly` and
`PORTAL_COMPATIBLE` — a bug there silently promotes portal users into the full
app), and the currency conversion in `lib/currency.ts`.

That's maybe 150 lines of Vitest against the four places where a silent wrong
answer costs you real money or real access. The standing rule already says pure
logic gets a node script; this just makes those scripts permanent.

### 2. `useSupabaseTable` — the scheduled cliff

92 call sites, and it fetches **whole tables**. `CLAUDE.md` flags it,
`docs/plan-server-pagination.md` exists, and nobody has scheduled it.

Right now this is fine — your tables are small. It stops being fine without
warning, and it stops being fine first on `messages` and `activities`, the two
that grow with usage rather than with headcount. `messages` already has cursor
pagination in `lib/useChannel.ts`, so the pattern exists.

This doesn't need doing this month. It needs a **trigger**: pick a row count
(say 2,000 on any single table) and check it monthly. Cheap to monitor,
expensive to discover in production.

### 3. The 2,179-line project page

`projects/[id]/page.tsx` is 2,179 lines. `portal/page.tsx` is 1,337,
`schedule/page.tsx` 1,325, `recruiting/page.tsx` 1,258. Twenty-three files over
500 lines.

I'd normally push harder on this, but I'll be honest about the trade: these
files are readable, they're well commented, and splitting them has a real cost
in indirection. The one I would actually split is `projects/[id]` — at 2,179
lines it's past the point where you can hold it in your head, and it's the page
you touch most often.

The other twenty-two can wait for a reason to change them.

### 4. Thirteen `exhaustive-deps` suppressions

Eighteen `eslint-disable` comments, thirteen of them silencing
`react-hooks/exhaustive-deps`, spread across nine files including four in
`dashboard/page.tsx` alone.

Each one is individually defensible. Collectively they're a pattern, and the
pattern is "the dependency array is fighting us". That usually means state is
being derived in an effect that should be derived during render — which is
already a standing gotcha in `CLAUDE.md`, with the fix documented in
`lib/useChannel.ts`.

Worth one focused session auditing all thirteen. I'd expect half to dissolve.

### 5. Database security — three warnings, none critical

Ran the Supabase advisors against **production** just now. Read-only, no
writes. No ERROR-level findings, and no missing RLS anywhere — that's a good
result and it reflects real care.

Three WARNs:

- **`public.approve_task` is `SECURITY DEFINER` and callable by any signed-in
  user** via `/rest/v1/rpc/approve_task`. This is the one to look at. If the
  function does its own authorization check internally it's fine; if it assumes
  the caller was already vetted by the UI, it's a privilege escalation. I did
  not read the function body — **verify this one.**
- **`private.channel_slug` has a mutable `search_path`.** Low severity, one-line
  fix (`SET search_path = ''`).
- **Leaked password protection disabled.** You already reasoned about this — the
  generated 20-character passwords in the Add Member drawer are a better answer
  than HaveIBeenPwned checking, and they're free. No action; noting it so the
  warning doesn't get rediscovered every quarter.

Remediation links are in the Supabase dashboard under Advisors.

## Process — the thing that actually costs you

Three of the nine punchlist items were written as **diagnoses** rather than
symptoms, and the diagnoses were wrong or stale:

- Item 5 said the week grid has no collision clustering. It has correct
  clustering. The real bug is still unidentified.
- Items 4+8 said no shared `Checkbox` exists. One existed.
- Item 6 asked whether the History button "earns its place". It had no
  `onClick` at all — thirty seconds of reading would have answered it.

`CLAUDE.md` already names this: *"Several roadmap items dissolved on inspection
because the thing described didn't exist or was deliberate."* It keeps
happening because the punchlist is written from screenshots, at a moment when
the code isn't open.

**Do this:** write punchlist items as what you *saw*, not what you think is
wrong. "Four meetings at 15:30 render unreadably narrow, screenshot 7" costs
you nothing and can't send the next session down a wrong path. Keep the
speculation — it's genuinely useful — but label it as speculation, the way the
item 3 entry on the projects accordion already does. That entry is the model:
*"Suspect, unverified... guessing at a perf problem is how you end up
optimising the wrong thing."*

  `renameTeam`, the `TimePicker` scroll-lock write-up — that's institutional
  memory, and it's rare.

  That's the file working; the failure was mine for not reading it first.
- **Security fundamentals.** Both privileged API routes check the session
  *and* the role server-side. The service key is server-only. RLS has no gaps.
- **`ship.sh`.** Verification gate before push, with a comment explaining that a
  broken push means a broken deploy. Correct instinct.
- **The standing-gotchas list.** Every entry is a bug someone paid for once.
